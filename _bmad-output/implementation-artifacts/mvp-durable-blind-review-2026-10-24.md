## Findings

- Independent durable diary owners can silently overwrite each other's accepted changes. `mobile/feature/photo-analysis/src/commonMain/kotlin/com/supernutrition/feature/photoanalysis/LocalUserData.kt:14-18` creates a new cached `MealDiary` for every composition; `MealDiary.kt:16` loads once and `:48` writes its own entire snapshot. Android creates that composition per Activity ViewModel at `mobile/feature/photo-analysis/src/androidMain/kotlin/com/supernutrition/feature/photoanalysis/PhotoAnalysisComposeActivity.kt:563-575`, while all production compositions select the same filenames in `AndroidLocalUserData.kt:10-12`. The manifest exposes this Activity with `singleTop` at `mobile/apps/androidApp/src/main/AndroidManifest.xml:10-13`. A concrete reachable trigger is launching that exported component twice with `Intent.FLAG_ACTIVITY_NEW_TASK | Intent.FLAG_ACTIVITY_MULTIPLE_TASK` (`0x18000000`); singleTop applies within each separate task, so each receives its own ViewModel. Open both before either saves, save a meal in task A, then save a different meal in task B. A lock around individual `load`/`save` calls does not protect this read-modify-write transaction: both owners loaded `[old]`, and B's accepted save replaces `[meal A, old]` with `[meal B, old]`. A deletion can likewise be resurrected by a stale owner. The public SharedKit production factory also creates independent owners of the same documents, although the submitted Swift root currently calls it only once. Acceptance: two simultaneously live Android tasks, plus a two-owner shared-store unit fixture, must preserve interleaved adds/deletes or reject a stale write visibly; establish one process-wide document authority or an explicit revision/CAS transaction rather than relying on AtomicFile's I/O lock. The launch sequence is a proposed reproduction, not an executed device result in this review.

- Android can report a failed replacement after it has already committed the new document. In `mobile/platform/photo-android/src/androidMain/kotlin/com/supernutrition/platform/photoandroid/AndroidPrivateDocumentStore.kt:41-51`, `finishWrite` commits before the verification read. If `openRead` or `readBoundedDocument` then throws `IOException`, the catch returns `false`; calling `failWrite` after a finished replacement cannot recreate the previous base bytes. The same disagreement is possible when the post-commit comparison returns false at `:47`. `MealDiary.kt:125-139` and `LocalProfile.kt:23-35` consequently retain the old in-memory value, while the next process can restore the newly committed edit/deletion that the UI said failed. This is a static failure-path finding, not an observed disk fault. Acceptance: inject a verification-read failure after a successful replacement and prove that a reported failure preserves the previous durable document, or expose an explicit indeterminate-commit/reload state instead of claiming the previous value is unchanged.

- A source or licence link can crash the authoring/details surface when the device has no HTTPS handler. `mobile/feature/photo-analysis-ui/src/commonMain/kotlin/com/supernutrition/feature/photoanalysis/MealCatalogSourceInfo.kt:46-47` uses `LocalUriHandler.openUri` directly, and `:90-96` invokes it from the button without handling its unavailable-handler exception. The existing Profile legal-link implementation already handles this exact native condition at `ProfileScreen.kt:124-133`, but the new source links do not share that recovery. `MealCatalogUriHandlerTest.kt` covers only a successful handler. Acceptance: a `UriHandler` that throws `IllegalArgumentException` must leave the source sheet and unsaved meal intact and display an actionable link-opening failure; retain a successful-handler assertion too.

- A transient read failure permanently disables the diary/name for the retained session. `mobile/feature/photo-analysis/src/commonMain/kotlin/com/supernutrition/feature/photoanalysis/MealDiary.kt:103-122` sends both corrupt data and ordinary I/O failures through a `writable = false` latch, and `LocalProfile.kt:39-60` does the same. Neither class exposes a reload/retry operation, and their mutation methods never retry the read. The Android owner survives Activity recreation; iOS retains its owner for the app lifetime. Therefore a temporary storage unavailability remains unrecoverable even after the file becomes readable, and opening the form or retrying Save cannot recover it. Complete iOS file protection is another reason to distinguish temporary unavailability from malformed bytes. Acceptance: a store that fails its first read and subsequently returns a valid document must recover through an explicit safe reload without process termination, while a malformed document remains preserved and cannot be overwritten by an empty fallback.

- Chooser paging limits composition only after all search results have already been queried synchronously. `mobile/feature/photo-analysis-ui/src/commonMain/kotlin/com/supernutrition/feature/photoanalysis/MealCatalogChooser.kt:53-55` runs search inside composition for every changed query; `:76` takes the visible page afterward. `mobile/data/nutrition/src/commonMain/kotlin/com/supernutrition/data/nutrition/SqlDelightUsdaCatalog.kt:25-31` performs a separate synchronous SQL lookup for every matcher hit before returning that list. A broad prefix can therefore issue many more than the visible 20 row queries on Main per keystroke. Background initialization does not address this later work. This is an unmeasured performance concern, not a measured SLO breach. Acceptance: use a counting source/driver and a broad real-catalog query to demonstrate bounded initial-page materialization and responsive input; serialize/cancel query work safely if it moves off Main, and discard stale query responses.

- Home resolves nutrition for the complete retained history before filtering to today's entries. `mobile/feature/photo-analysis/src/commonMain/kotlin/com/supernutrition/feature/photoanalysis/MealDiaryHomeModel.kt:13-18` first calls `mergedMealHistory` for every record. `mobile/feature/photo-analysis-ui/src/commonMain/kotlin/com/supernutrition/feature/photoanalysis/MealHistoryModels.kt:50-58` then performs a source resolution for each bound saved record, and only `MealNutritionProjection.kt:49-50` filters the resulting projections by day. Both hosts invoke this from composition, including clock refreshes. With durable history the work grows toward the 10,000-record bound even when only one meal contributes to today's metrics. This is a static unnecessary-work finding; latency was not measured. Acceptance: an injected counting catalog with many historical bound meals and one current-day meal should require only current-day resolutions for Home, while preserving merged-ID supersession, count and unknown-total semantics.

- The new durable document I/O remains synchronous on the UI path. `MealDiary.kt:125-127` encodes and saves the complete document directly; `LocalProfile.kt:20-24` also saves directly. `mobile/feature/photo-analysis-ui/src/commonMain/kotlin/com/supernutrition/feature/photoanalysis/MealForm.kt:75-82`, `MealDetailsScreen.kt:150-154`, and `ProfileNameEditor.kt:61-69` call these operations from input callbacks. On Android, `AndroidPrivateDocumentStore.kt:39-47` includes a disk write, `fd.sync`, rename and complete verification read before returning; initial `LocalUserData` construction synchronously loads documents before the host renders. The diary permits a 4 Mi-character document, so this is more than the small catalog-owner bookkeeping deliberately kept on Main. This is an unmeasured responsiveness concern. Acceptance: exercise a near-limit document and an intentionally slow store with a UI responsiveness/StrictMode check; perform serialized storage work off Main and publish success/failure only after the transaction completes, preserving failed drafts and deletion state.

- The Android journey test now mutates the production durable diary and assumes that diary was initially empty. `mobile/apps/androidApp/src/androidTest/java/com/supernutrition/android/MealDiaryJourneyInstrumentationTest.java:30-51` launches the target application, adds/edits/deletes a record, and asserts `MEAL_HISTORY_EMPTY`, with neither an isolated storage namespace nor `finally` cleanup. New production selection in `mobile/feature/photo-analysis/src/androidMain/kotlin/com/supernutrition/feature/photoanalysis/AndroidLocalUserData.kt:10-12` routes that flavor to the user's real durable filenames. Clearing the Activity task at test line 33 does not isolate those documents. An existing legitimate meal makes the final assertion fail; any earlier assertion failure can leave synthetic QA entries in the user's diary across restart. Acceptance: run against a preseeded unrelated meal and deliberately fail mid-journey; the fixture must clean up only its own IDs and preserve the preexisting document/name byte-for-byte where untouched, without clearing app data or depending on an empty production diary.

- The selected-product form tells the user grams are optional even though Save requires them. `mobile/feature/photo-analysis-ui/src/commonMain/kotlin/com/supernutrition/feature/photoanalysis/MealFormCopy.kt:10` still says “Optional, for the whole meal”, and `:20` tells the user to enter a positive portion “or leave it empty”. These strings are rendered unchanged for a selected product by `MealForm.kt:107` and its error presentation at `:76-78`, while `mobile/feature/photo-analysis-presenter/src/commonMain/kotlin/com/supernutrition/feature/photoanalysis/MealCatalogBindingValidation.kt:16-18` rejects a selected product with empty grams. The chooser's separate required-grams sentence does not remove these contradictory instructions beside the field and after rejection. Acceptance: selecting a product switches the field help and missing-grams error to an explicit required single-product weight; removing the selection restores the optional whole-meal wording.

- The expanded native-evidence invalidation lists still have no executable consumer. The change adds UI paths at `mobile/config/quality/native-gaps.toml:39`, `:59`, `:69`, `:93`, `:121` and `:135`, but the local validators do not read `invalidated_by` at all. `mobile/build-logic/src/main/kotlin/com/supernutrition/buildlogic/MobilePolicyValidator.kt:644-660` validates attestation field presence/digest shape and age; `CoverageVerifiers.kt:45-59` likewise accepts a fresh success record without comparing the declared source paths or candidate artifacts. Repository searches found `invalidated_by` only in the manifest, not executable mobile/scripts/evidence code. This enforcement gap predates the patch, but the new lists do not close it and cannot substantiate current UI/native coverage after a source change. Acceptance: with a fresh valid attestation, changing a file under one declared glob must reject the evidence until the relevant native run produces a new binding; an unrelated change must not invalidate it. Keep the independently documented current expiry failure separate from this missing source-change enforcement.
