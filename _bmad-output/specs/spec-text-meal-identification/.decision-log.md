# Decision log — SPEC-text-meal-identification

## 2026-07-27 — create

Input was multi-source and in-chat: a review of merged PR #5, the SuperNutrition planning corpus (PRD, architecture spine, epics, UX), and a stated product direction that photo identification should fall back to text, inferred locally where possible through an on-device LLM. Slug taken as `text-meal-identification`; the input carried no upstream slug to inherit. Rich input, so extraction was direct — no elicitation, express mode not needed.

Six capabilities. CAP-1 (deterministic floor) is deliberately separated from CAP-3 (model path) rather than folded together, because the input's own conditions require it: UJ-4 places the offline fallback on a lower-tier device, so the journey that most needs text identification is the one least able to run a model. That separation is the spec's central structural decision and drives the CAP-1-can-ship-alone question recorded under Open Questions.

Three spec-authored companions. `search-mechanics.md` holds the deterministic floor because it is a multi-row decision matrix that would have bulleted into sub-bullets inside Constraints; it also fills a real gap, since the planning corpus specifies the search *surface* but never its behavior. `contract-v2.md` holds the modality migration because it is a versioned change with an ordered sequence. `failure-modes.md` holds six named failures with controls, in table-adjacent form. Three adopted companions — ARCHITECTURE-SPINE.md, prd.md, EXPERIENCE.md — are referenced, not copied; they are owned by their originating skills and downstream must read them for the invariants this spec builds on. `sources:` is empty: nothing was fully absorbed, since every referenced artifact retains independent downstream value.

**Pass 1 — Coherence.** Rules 1–6 hold. Every capability carries both `intent` and `success` (rule 1). Intents state WHAT; the FTS5 choice, ranking order, and migration sequence are HOW and sit in companions (rule 2). Each constraint rules something out — the CAP-1-cannot-depend-on-CAP-3 constraint forbids a model-only design, the v1-frozen constraint forbids an in-place contract edit, the never-defaultable constraint forbids collapsing the review step (rule 3). Six non-goals, several lifted from existing PRD §5 exclusions so this spec cannot silently widen release scope (rule 4). The success signal is a demonstrable scenario with named conditions — offline, lower-tier, no model — rather than a sentiment (rule 5). IDs CAP-1..CAP-6 are new and unreused (rule 6). Prose was cut on a second pass; the Why paragraph retains backdrop only where it carries the load-bearing fact that search is the terminal fallback for four distinct journeys (rule 8).

**Pass 2 — Preservation.** Every load-bearing claim from the input landed. The contract-v1-is-photo-only blocker → CAP-4 and `contract-v2.md`. The plausible-but-wrong-record risk → CAP-5 and FM-1. The device-tier tension → CAP-1/CAP-3 split, the second constraint, and FM-4. The unspecified-search gap → CAP-1 and all of `search-mechanics.md`. The PRD non-goal permitting an additional-but-not-sole model path → the third non-goal. AD-40's defaultable allowlist → FM-2. AD-6's closed trigger set → the sixth constraint and the routing section of `contract-v2.md`. AD-12's country/language independence → the seventh constraint and the language section. Free-text sensitivity, which no existing rule anticipates because the corpus assumes a photo-only product, → the eighth constraint and FM-5. Wrapper-only content dropped: the PR-review narrative framing, comment IDs, and the traceability audit tally, none of which bind a downstream decision.

Five open questions recorded rather than guessed: remote text inference scope, multi-item parsing scope, catalog-language matching, gate ownership for identification quality, and ship order. Multi-item scope is the sharpest — it materially changes CAP-2, the serving-confirmation surface, and the AD-19 aggregation path, and FM-6 exists specifically because an implementer could reasonably build either behavior today.

Four assumptions recorded: on-device-only inference, floor-required-on-every-device, reuse of existing surfaces rather than parallel screens, and the `PhotoInferenceEngine` rename riding the v2 migration.

## 2026-07-27 — update: Q2 resolved (segmentation)

Open Question 2 asked whether multi-item text resolves to several candidates or whether v1 is single-item. Checking the corpus collapsed half of it: the photo path is already multi-item — FR-13 reviews and removes Candidate**s**, FR-16 preserves "per-item and aggregate provenance", FR-17 keeps unresolved matches "partial", and AD-19 owns "per-item-to-meal aggregation". A single-item text path would therefore not be a fallback for the photo path at all, since a user could not reach by typing the result the camera would have produced, and the spec's own success signal is a two-item meal. Single-item was never a live option; the spec asked the question badly.

The real decision was who splits the description into items. The deterministic floor answers for itself — a search query returns one record, so the floor accumulates items one at a time, and that path must exist regardless because CAP-1 cannot depend on CAP-3. The open part was only the model path.

Decision: the engine proposes a segmentation and the user can merge, split, remove, or add items before confirming any of them. Rejected: engine-segments-without-adjustment, which controls FM-6 only by abstention and gives the user no way to repair a bad split; and user-segments-only, which makes the model path barely better than the floor beneath it while spending the interaction budget NFR-24 and UX-DR37 protect.

Changes: CAP-2 restated as one candidate group per detected item; CAP-7 added for segmentation adjustment; a constraint added making segmentation a proposal that is never silently reduced; FM-6 rewritten so the control is editability rather than scope choice, and tied back to FM-1's shared instinct that the engine proposes and the user decides; `contract-v2.md` gained a segmented-response section requiring each group to carry the description span it came from, which is what makes the split editable with visible provenance; `search-mechanics.md` gained a multi-item section showing the floor and the model path converge on one confirmed item list. Q2 removed from Open Questions; four remain.

## 2026-07-27 — update: OQ-1, OQ-2, OQ-4 answered

**OQ-1 — remote text: yes.** Added CAP-8. Remote text reuses AD-6's existing closed trigger set rather than widening it, so local still runs first and `RemoteEligibilityReason` gains no value; "remote text identification" moved out of Non-goals, replaced by the narrower non-goal that remote is never tried before an on-device attempt. One finding fell out of implementing this: `consentCopyVersion` in the country profile denotes the reviewed *photo*-transfer explanation, and the reviewed copy says a smaller copy of the photo is sent. That sentence is false for a typed description, so the photo disclosure cannot authorize a text transfer. A text-specific copy version is now a constraint and is enforced in `contract-v2.md` as a fail-closed mismatch.

**OQ-2 — multilingual for Tier 1 and Russia.** Added CAP-9 and a per-market language matrix in `search-mechanics.md` declaring catalog language, accepted input languages, script, morphology, and synonyms as versioned data rather than conditionals in search code. This overturned an earlier decision: the create pass chose "no stemming in v1", handling plurals through synonyms. That holds for English and fails for Russian, whose nouns inflect across cases — курица, курицы, курицу, курицей are one food, and enumerating every form of every record as a synonym is not maintainable. Morphological normalization is now per-market and declared, and cross-script entry was added so a Cyrillic record is reachable from Latin-script typing. Transliteration feeds the fuzzy tier rather than claiming exact matches, since it is many-to-many and should never outrank a genuine exact match in the record's own script.

Recorded as an assumption rather than a scope decision: Tier 1 in the corpus is the United States, Canada, United Kingdom, Australia, and New Zealand with an English-first beta, so "multilingual for Tier 1 and Russia" adds a non-English catalog language, a second script, and a market outside the current high-income framing. Gate G-1 owns the launch list, so the spec fixes the language and script requirements and leaves the country list to that gate.

**OQ-4 — plain search box first.** Added as a constraint: CAP-1 ships before and independently of CAP-2, CAP-3, and CAP-7. It already closes the specification gap that motivated the spec and is the only path that works on every device.

**OQ-3 — deferred, made decidable.** Left open at the reader's request, with a suggested starting point rather than a guessed number: measure the "not sure" rate per market language against the existing evaluation corpus, which already runs local-only, remote-only, hybrid, and manual baselines, and give it the same owner pairing that owns accuracy claims today.

**Two new questions raised by the answers.** OQ-5 asks whether Russian users' typed text may be processed outside Russia, given that Russian law on personal data is generally understood to require storage of citizens' personal data in-country; whether a meal description is personal data is a legal judgement this spec does not make, and the consequence is whether Russian remote text is on-device-only. It also flags that Russia sits outside the corpus's high-income Tier 1 framing, which G-1 should hear. OQ-6 asks which languages specifically per market, since "multilingual" fixes the requirement but not the list, and each language costs a synonym set, inflection handling, and query fixtures per catalog — roughly linear, and the real driver of search effort.

Capabilities now CAP-1..CAP-9; constraints 12; non-goals 6; open questions 3 (OQ-3, OQ-5, OQ-6).

## 2026-07-27 — update: OQ-5 resolved structurally

OQ-5 asked whether Russian users' typed text may be processed outside Russia. Investigating it showed the question was framed wrongly in two ways.

First, it conflated language with market. Supporting Russian is a product capability costing synonyms, inflection handling, and fixtures; operating in Russia is a legal position. The language matrix already separated catalog language from accepted input languages, so Russian-language support needs no residency determination at all and ships in story E7.3.

Second, the question predates this spec. The product already transfers photos to a first-party gateway under AD-13, so any market with residency constraints constrains remote photo exactly as it constrains remote text. Typed identification surfaced the question rather than creating it, which means the spec was the wrong owner.

What was actually missing was structural: the spine names `MarketPolicyResolver` as sole resolver of `MarketJurisdiction` and `ProcessingRegion`, but nothing defined the data it resolves against. Without that, processing region resolves from whatever configuration happens to contain and no rule prevents a market being served by a region its law does not permit.

Written: `market-processing-policy.md` specifying `contracts/market-policy/v1`, following the established `contracts/interaction-policy/v1` pattern from AD-40/AR-47/E1.5. Every market defaults to `unresolved` and permits no remote transfer of any modality; absence, unresolved, and expiry are equivalent at resolution time; postures are set only by named legal review with an approver and mandatory expiry, and never widened as a side effect. Photo and text permissions are independent with their own consent copy versions. Accepted input languages are independent of posture in both directions. Catalog choice cannot move any of it. Bound by AD-41, AR-53, NFR-27, and story E1.6, placed in E1 beside the interaction policy it parallels rather than in E7.

Russia now enters as `unresolved` like every other market, so nothing blocks pending review, and the deterministic floor plus on-device identification keep any fail-closed market fully usable. The remaining question for counsel — whether an account-free description or photo carrying an opaque attempt ID and short-lived attestation token is personal data of a Russian citizen — sets one market's posture and changes no rule.

Open questions now three: OQ-3 abstention threshold, OQ-5 as a G-1/G-4 referral rather than a spec blocker, OQ-6 per-market language list.

## 2026-07-27 — update: OQ-6 answered, OQ-3 closed

**OQ-6 — English, Spanish, Russian.** These three exercise every branch of the language matrix rather than three points on one branch: English needs nothing beyond plurals, Spanish needs diacritics and light stemming for gender and number, Russian needs full lemmatization across cases plus cross-script entry. Shipping all three proves the matrix design. A fourth language matching one of these profiles is incremental; one matching none is a new profile and a new decision.

Two consequences went into `search-mechanics.md`. The synonym layer is keyed per (catalog, input language) pair rather than per language, because an accepted input language does not imply a catalog written in it — Spanish and Russian speakers in the United States both search against English USDA records, so each pair needs its own mapping onto that catalog's canonical IDs and its own fixtures. And Spanish regional naming costs more than Spanish grammar: palta against aguacate, frijoles against judías against porotos are different words for one food, not spellings or inflections. Resolved by accepting every regional variant onto one canonical ID rather than selecting a dialect per market, since search exists to find things and inclusiveness is free at query time; display continues to use the catalog record's own name. The same pattern covers English aubergine/eggplant and Russian regional and Soviet-era names.

**OQ-3 — closed as over-engineered.** The question asked who owns the acceptable "I'm not sure" rate and what the number should be. On review that proposed governance for something a labelled fixture set already pins, and would have committed to a threshold before any data existed to choose one. The safety direction is already carried by testable invariants — FM-3 requires abstention over a guess, FM-1 requires confirmation before a record binds, FM-6 forbids silent reduction.

What replaced it is a test-design requirement rather than a gate: the identification fixture set declares expected outcomes in both directions, entries that must resolve to a named canonical ID and entries that must abstain. That two-sided shape is the real content. A fixture set built only from resolvable cases rewards guessing and quietly pressures the engine toward FM-3; should-abstain entries make over-confidence a test failure instead of a judgement call. Abstention rate is reported against the evaluation corpus alongside the existing baselines as a measurement, not a release gate — nothing blocks on it because the deterministic floor always answers. Recorded in FM-3 and in story E7.4's acceptance criteria; no new gate, owner, or pre-committed number.

Open Questions reduced to OQ-5 alone, which remains a G-1/G-4 referral rather than a spec blocker. Answered and closed questions live here rather than in the SPEC, since that section is for gaps still needing a decision.

The spec scoped CAP-4 as an amendment to contract v1, landed before story 3.1 froze the inference ports, on the reasoning that nothing implemented the contract yet so nothing needed migrating. Story 3.1 has since shipped and that reasoning no longer holds.

Verified against `origin/main` at `6de40bdf`: `contracts/inference/v1/RELEASE.md` describes an "Immutable, language-neutral, data-only contract release"; `compatibility-matrix.toml` records `digest = "3634abd47f88682cc0953cab229d932f4be26e7f0f76419877dcfe1ce229cba3"` over the schema, matrix, and canonical fixtures; `schema.toml` sets `contract_id = "photo-inference-engine"`, `request = "opaque-photo-ref-plus-immutable-attempt-context"`, and `incompatible_change = "new-major-release"`; and `InferenceContract.kt` declares `PhotoInferenceRequest(val photoRef: PhotoRef, …)` with a non-nullable photo. ## 2026-07-31 — update: Spanish dropped, English and Russian remain

OQ-6 was answered English, Spanish, Russian. Spanish is now out of scope. The change is small in code and worth recording precisely, because a dropped language takes its coverage with it.

Removed: Spanish alternate names from the seed catalog, and the Spanish display names it had acquired -- "Aguacate" and "Frijoles negros" became "Avocado" and "Beans, black". Two tests were rewritten rather than deleted, since the mechanism they proved still needs proving: the regional-variant test moved from palta/aguacate to aubergine/баклажан, and the Spanish seed test became a Cyrillic-and-Latin-script one. Dropping a language should not cost coverage of the mechanism that language happened to demonstrate.

Two consequences that are not obvious from the diff.

The matrix is now proven at two points rather than three. English needs nothing beyond plurals and Russian needs full lemmatization with cross-script entry, so they sit at opposite ends. Spanish was the only target requiring light stemming with diacritics, and that middle profile is now designed and untested. A future market landing on it is a new decision rather than an increment, and the language matrix says so.

The diacritic fold in normalizeForSearch loses its main justification. Cyrillic does not use Latin-1 accents, so the 39-character table now earns its place only through English loanwords such as café and jalapeño, and through Russian ё/е. It is close to unexercised. It stays because a future accented market would need it and because removing it is cheap later, but it is a deletion candidate rather than load-bearing, and that should be an explicit decision rather than something discovered.

Nothing else changed. The synonym layer, the per-(catalog, input language) keying, and the requirement that every record carry alternate names are all independent of which languages are targeted -- English alone needs them, since aubergine and eggplant are the same food.

## 2026-08-01 — a food named twice is two items, not one

An adversarial review of E7.2 raised this three times and its own refuters split two-to-one against it, which is the honest signal that it was a design question rather than a defect. It is recorded here because the answer changes a contract shape and because the reasoning is not recoverable from the diff.

The question: a description can name one food twice — "rye toast and rye bread" both resolve to `food:bread-rye` against the seed catalog. Is that one item or two? Put another way, does identity resolution own quantity, or does serving confirmation?

It was settled by execution rather than preference. `DeterministicTextEngine.identify("rye toast and rye bread")` already returns two `DetectedItem`s carrying distinct spans, `(0,9)` and `(14,23)`. The engine path had therefore already answered "two". Two other places disagreed with it, and neither disagreement was deliberate.

`SegmentationReview` keyed add/remove/confirm/merge on `canonicalItemId`, so the two instances were indistinguishable to every editing operation: `remove("food:bread-rye")` left zero items where one was intended, and `confirm` on one confirmed both. That is CAP-7 read literally — removing an item the engine invented must not discard an item the user already confirmed. Edits now identify an item by the item. The span is what tells two instances apart, and it is also the provenance the user is shown, so it is the right identity for an edit rather than a convenient one.

`TextIdentification.fallBack` collapsed duplicates with `distinct()` and returned bare canonical IDs. `TextIdentificationOutcome.Floor` now carries `DetectedItem`s exactly as `Items` does, so both paths report the same shape and duplicates survive on both. This also closes a separate gap: a floor result previously had no spans at all, so the CAP-7 correction surface could not anchor to the words a user typed, and the floor is the path UJ-4 most depends on.

What this does not decide: how a confirmed duplicate aggregates into a meal total. Two items resolving to one record still need one serving decision each, and that belongs to serving confirmation rather than to identification. Nothing here binds a nutrition number, so the question stays open where it belongs.

The structural point is worth keeping separate from the outcome. The engine and floor paths disagreeing is the same failure that produced the original defect this story was reopened for — the floor did not segment because only the engine did, and nobody had made them share the code. They now share `TextFragments`, share the outcome shape, and share the duplicate semantics. Two paths that must agree should be hard to make disagree, not merely documented as agreeing.

## 2026-08-01 — closing the duplicate-aggregation question

Left open when duplicates were made two items on every path: how a confirmed duplicate aggregates into a meal total. It turns out not to need a decision, and recording that is worth more than leaving it listed as open.

Nothing special happens. AD-19 already aggregates per-item to meal totals and FR-16 already keeps per-item provenance, so two items that resolve to one record are simply two items, each with its own serving, and the totals add. There is no duplicate case in the aggregation layer to handle.

The only real question was whether confirmation should merge them silently, and it should not — that is the `distinct()` error again, deciding for the user. CAP-7 already ships the honest alternative: `merge` exists, so someone who meant one thing says so explicitly and someone who ate two portions is not overruled.

## 2026-08-01 — Spanish restored; the matrix now has three languages

Spanish was dropped on 2026-07-31 and is a target again. Recording the reversal rather than quietly editing the earlier entry, because the entry explains what the removal cost and that reasoning is exactly what makes restoring it worthwhile.

Restored as alternate names, not display names. The 2026-07-31 removal had also reverted display names — "Aguacate" and "Frijoles negros" back to "Avocado" and "Beans, black" — and that part stands: `CatalogRecord` documents alternate names as matched but never displayed, so someone typing *aguacate* reaches the record and then reads the catalog's own name for it rather than a translation the catalog cannot vouch for. Spanish is searchable again without the catalog claiming to speak it.

Two things the earlier entry recorded as losses now reverse.

The middle of the morphology matrix is occupied again. English needs nothing beyond plurals, Russian needs full lemmatization, and Spanish sits between them on light stemming with diacritics — the profile the earlier entry called "designed and untested". Every declared profile now has a language exercising it, which is the difference between a matrix and a list of two extremes.

The diacritic fold is load-bearing rather than a deletion candidate. With Spanish gone it survived only on English loanwords and Russian ё/е, and was explicitly marked for removal if no accented market ever arrived. *Berenjena*, *plátano*, and *jalapeño* now depend on it, and a user typing without accents must still reach the record — which is the case the fold exists for.

Unchanged: the quantity and separator vocabularies stay English-only. Spanish needs its own, as Russian does, and both belong in the per-market language matrix as data rather than as constants in search code. Adding a third language to the catalog does not change where those lists should live, and E7.3 now covers three languages instead of two.
