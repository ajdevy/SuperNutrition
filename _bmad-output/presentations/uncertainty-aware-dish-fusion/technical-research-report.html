Главная проблема: один список смешивает разные типы доказательств.

01 · Situation

Пользователь хочет понять состав блюда, а получает смесь сигналов.

В текущем PoC dish classifier, detector и recipe knowledge оказываются в одном пользовательском результате. Поэтому «pork chop» может соседствовать с «orange», а отсутствие «broccoli» выглядит как доказательство отсутствия.

1

Блюдо — это гипотеза

pork_chop говорит, какое блюдо больше всего похоже на фотографию. Это не маска и не список реально видимых продуктов.

2

Детектор — это отдельный сигнал

orange — предложение визуального детектора. Оно требует локализации и калиброванного порога перед тем, как попасть в основной overlay.

3

Рецепт — это контекст

broccoli может быть составно правдоподобен, но не локализован. Контекст должен поддержать review, а не выдать визуальный факт.

Один confidence не может честно описать одновременно «модель видит объект» и «этот объект типичен для блюда».

02 · Friction

Hard-prior фильтр делает ошибку тихой и необратимой.

Он кажется простым: взять dish top‑1, оставить только ожидаемые ингредиенты и убрать остальное. Но один и тот же результат может означать три разные вещи — и для каждой нужен свой UX и свой quality gate.

Prior-only knowledge

Брокколи типична для состава, но рецепт сам по себе не доказывает её наличие на фото.

03 · Change

Решение: calibrated top‑k late fusion.

Сохраняем независимые каналы, калибруем их отдельно и только потом объединяем в детерминированном fusion layer. Dish prior может ранжировать и поддерживать, но не может «нарисовать» регион на фото.

04 · Claim semantics

Каждому типу доказательства — свой статус.

Это не просто переименование. Разные статусы позволяют UI, nutrition binding и debug-режиму принимать разные решения, не теряя исходные model outputs.

05 · Proof

Решение принимаем по измеряемому риску, а не по более длинному списку.

Мы начинаем не с нуля: v2 contract и G-3 baseline уже задают production boundary, runtime budgets и честное ограничение текущих моделей. Fusion thresholds всё ещё нужно получить из отдельного slice report.

Production boundary уже есть

  • v2 result: components, abstention или typed failure.
  • Visual claim: `VisibleComponent.confidence` + `ComponentVisibility`.
  • Composition-only: отдельный review/debug envelope, не overlay.
  • Compatibility: additive optional extension only; required-field changes need a new major.

06 · Action

Следующий implementation slice — зафиксировать смысл до настройки весов.

Полный joint model — долгий future track. Ближайший безопасный выигрыш даёт контракт, replay fixtures, calibration и shadow mode поверх уже существующих model adapters.

R1

Delta к v2 contract

Reuse existing confidence, visibility и provenance; composition-only states держать отдельно до additive extension.

R2

G-3 baseline + ablation

Пять политик поверх существующих device/model measurements и fixed conflict slices.

R3

Separate calibration

Dish и detector калибруются независимо; raw scores не складываются.

R4

Top‑k fusion

Small deterministic baseline или meta-model с отдельными claim gates.

R5

Review-safe UI

Overlay только для VISUAL_DETECTED; остальное — отдельные статусы.

Definition of Done для research flag

Host benchmark + Android device evidence + iOS evidence when available + contract/UI tests; complete provenance; zero stale-result regressions; rollback к старой policy остаётся возможным.

Appendix

Что подтверждено и где остаётся неопределённость.

Архитектурный вывод имеет высокую техническую уверенность. Конкретные weights и thresholds требуют project-specific calibration set и ещё не являются production evidence.

Ключевые источники

  • FoodSeg103 benchmark
  • Nutrition5k official repository
  • UECFoodPix official dataset
  • Modern neural network calibration
  • Selective prediction / reject option
  • ONNX Runtime Mobile
  • Existing inference-evidence/v2 schema
  • Existing G-3 device baseline

Ограничения ресерча

  • Новый 300-meal weighed corpus не собирался. Для этого отчёта использованы публичные источники и curated conflict cases.
  • Публичные датасеты не равны user meals. Есть ограничения по cuisine, domain shift и визуальной наблюдаемости скрытых компонентов.
  • Thresholds ещё не production-ready. Они должны появиться после baseline, calibration и slice report.
  • Доказательство не должно быть одной цифрой. Нужны claim-specific states, provenance и возможность abstain.
